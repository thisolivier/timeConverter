- [x] **7. Tappable candidate chips for ambiguous zones (P4)** — *(M)* Render `Prompt.ambiguousZone`'s `[ZoneChoice]` as a row of tap-to-replace buttons (`Chicago −5` `Shanghai +8`) under the prompt line; a tap rewrites the ambiguous token *in the input string* (`9am CST to IST` + Chicago → `9am Chicago to IST`), so the typed sentence stays the single source of truth, the re-parse happens naturally, and the user lands on the next prompt if there is one. Same SwiftUI buttons on iPhone, iPad and Mac — no forked model. M rather than S because the tap needs a character range the pipeline currently discards: `InputTokenizer.normalize` lowercases and collapses whitespace, and `Prompt` carries only the normalized token plus a `ZoneSide`, so this wants either a range-carrying tokenizer or a side-aware locate against the raw string (`9am CST to CST` must rewrite the correct side) — plus `ConverterDisplayState.problem(String)` becomes a structured value so the view keeps holding no logic, plus presenter tests. Scope note: prompt tone/styling (proposal #3, de-redding the prompt line) is *not* in Olivier's decision list, so the chip row ships inside the existing styling. See `docs/ux-v1-proposal.md` #1 and its Decisions section.
- [x] **8. 600 ms debounce on prompt display** — *(S)* While the field is focused and the input does not yet parse, hold the prompt back for ~600 ms (the decided parameter) so ordinary typing stops flashing a prompt per keystroke. **Results still render instantly** — the debounce covers prompt display only, never conversions. Small but not free: a cancellable task per edit in the view layer, with the delay injectable so the behaviour stays unit-testable, and one decision to make explicit — a chip tap from item 7 and `onSubmit` should bypass the wait and show the next prompt immediately, since the user has just acted rather than typed. Tight pair with item 7: both live in the same prompt-display area, so build them together. See `docs/ux-v1-proposal.md` #4 and its Decisions section.
- [x] **9. "Did you mean…" chips for unknown zones (P5)** — *(M, top of M)* On `Prompt.unknownZone`, run the token through an edit-distance pass (≤2) over the vocabulary the resolver chain can already see and offer the top ≤3 as chips (`Lodnon` → `London?`), reusing item 7's tap-to-replace mechanic verbatim — zero new UI concepts. **Never auto-accept**, not even when exactly one candidate is within distance 1: decided policy is always require the tap, because a silently corrected wrong city produces a conversion that looks right. The code change is an *additive* suggestions/vocabulary capability beside `ZoneResolver.candidates(for:)`, so the parser stays pure: `AliasZoneTable`, `CountryZoneTable` and `TimeZoneDatabaseCityResolver.identifiersByCityName` are already enumerable statics and `TimeZone.abbreviationDictionary` is enumerable, but `OfflineFallbackZoneResolver.identifiersByPlaceName` is private and must be exposed; then ranking, dedupe across chain levels, the ≤3 cap, and a check that a roughly thousand-entry scan per prompt is cheap (item 8's debounce helps). The editorial half is the real cost — deciding which vocabulary is worth suggesting at all, so that `cst` does not offer `cet`. **Item 6 (QA-candidates review) feeds this item's vocabulary**: the typo and punctuation cases in `docs/qa-input-candidates.md` are the source list for what the suggester must catch — cross-referenced, not merged. See `docs/ux-v1-proposal.md` #2.
- [x] **10. Autofocus the input on launch and foreground** — *(S)* `@FocusState` the `TextField` on appear and on return to `.active` via `scenePhase`, so launch-to-typing is zero taps on iPhone and iPad and the Mac window arrives ready to type — for a typed-input tool this *is* the access story. S: a handful of lines in `ContentView`, the only care being not stealing focus mid-session on Catalyst and not disturbing the DEBUG `-initialInput` prefill. Build it before items 11 and 12, which both deep-link into exactly this state. See `docs/ux-v1-proposal.md` #5.
- [ ] **11. iOS launchers: Control Center control + App Shortcut** — *(M)* An iOS 18+ `ControlWidget` button ("Convert a time") plus an App Shortcut phrase, both deep-linking into the app with the field focused (item 10), reachable from Control Center and the lock screen without home-screen real estate. Honest scope: launchers only — no widget can accept typed input, and display widgets are **dropped** as decorative, so nothing here touches the interaction model. M because the control needs this project's first *second* target: a widget extension in `project.yml` with its own bundle id, and the Release config signs manually against a named profile (`TimeConverter App Store`), so an extension means a second App ID plus distribution profile and a `scripts/ship.sh` run to prove TestFlight still validates. The App Shortcut half is an `AppIntent` plus URL handling and is nearly free — ship it as a first slice if extension provisioning fights back. See `docs/ux-v1-proposal.md` #6 and its Decisions section.
- [ ] **12. Mac menu-bar presence with a ⌃⌥T global hotkey (loadable AppKit bundle)** — *(L)* Option A from the proposal: keep the single Catalyst target and add a small bundle built against the macOS SDK, loaded at runtime, owning an `NSStatusItem` for the menu-bar icon and a Carbon `RegisterEventHotKey` registration for **⌃⌥T** ("T for time" — decided, not ⌃⌥Space), which activates the ordinary app window with the field focused (item 10). No floating panel in v1; the summoned thing is the identical app. L, and the bridge code (~150–250 lines) is the easy part — the unknowns are, in the order they should be retired: (a) expressing a macOS bundle target plus an embed-into-`Contents/PlugIns` copy phase in xcodegen and loading it from Catalyst across a shared protocol — `MenuBarExtra` is **not** available to Mac Catalyst, so there is no SwiftUI shortcut; (b) Carbon `RegisterEventHotKey` is a C API needing an event-handler bridge and raw keycodes (`kVK_ANSI_T` with `controlKey|optionKey`), chosen because it needs no accessibility permission; (c) signing and TestFlight-on-Mac for an embedded bundle, the biggest risk, since the Mac build ships through the same iOS TestFlight pipeline (`scripts/ship.sh`) and no project in `../musicLibrary/` has shipped an embedded AppKit bundle this way — budget a throwaway archive upload purely to find out. Accepted asymmetry: access differs per platform, usage never does. See `docs/ux-v1-proposal.md` "The Mac access-path decision" and its Decisions section.

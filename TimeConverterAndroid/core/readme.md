# core

The Kotlin twin of the Swift package `TimeConverterCore`: parser, engine and
presenter as a plain JVM library. No Android imports, so `scripts/test-android.sh`
runs the whole suite on the JVM in about a second. The app module renders
`ConverterDisplayState` and nothing else.

## Working patterns

- **Ported file for file, behaviour held by fixtures.** Each Kotlin file names
  the Swift file it ports; `fixtures/conversion-cases.json` (generated by the
  Swift core) is the contract, and `SharedFixtureParserTests` compares every
  case exactly. When the two disagree, Swift is right.
- **Pure.** `now` and the device zone are parameters everywhere; only the app's
  `ConverterScreenModel` reads the clock.
- **Resolution order is data.** `ZoneResolverChain.standard` is the list
  alias → abbreviation → tz-db city → country → gazetteer; the first resolver
  with a candidate answers, one candidate resolves, several prompt (P4).
- **The world clock is the converter, re-run.** Each row is
  `ConversionEngine.read` from local at the shifted wall-clock time to the
  favourite, with `ConverterPresenter.zoneLine` and a day marker measured
  against the real local today. The offset shifts the local wall clock and
  resolves through `WallClockResolver`; at zero `now` is read straight through.
  `SharedFixtureWorldClockTests` holds it to `fixtures/world-clock-cases.json`.
- **Shared resources, one copy.** `build.gradle.kts` puts the Swift core's
  `zone-names.json` and `fallback-cities.json` on the classpath straight from
  `TimeConverterCore/Sources/TimeConverterCore/Resources/`.

## Where the JVM differs from Foundation

- **Abbreviations.** `java.time` has no `TimeZone.abbreviationDictionary`, so
  `FoundationAbbreviationSnapshot` is that dictionary copied verbatim (51
  entries, macOS 26.2, 2026-10-28). Refresh it by printing the dictionary from
  a Swift script.
- **Identifier list.** `ZoneId.getAvailableZoneIds()` carries tzdata backward
  links that Apple's `knownTimeZoneIdentifiers` omits (`America/Buenos_Aires`,
  `Australia/NSW`, `Asia/Saigon`…). Step 3 drops them
  (`TimeZoneDatabaseCityResolver.LEGACY_LINK_IDENTIFIERS`), otherwise `buenos
  aires` would prompt and `nsw` would resolve. `Asia/Kolkata` is kept (Apple
  lists only `Asia/Calcutta`), so `kolkata` resolves at step 3 here and in the
  gazetteer on iOS: same zone, same display.
- **Raw-text offsets.** `RawTextRange` counts UTF-16 units; Swift counts
  Characters. They differ only when an emoji or a multi-scalar character sits
  before the token. Each platform applies its own ranges to its own strings,
  so chips are correct on both; only a fixture with such input would differ.
- **Capitalisation.** Chip labels use `FoundationCapitalization`, a port of
  `String.capitalized` (`Port-Au-Prince`, `U.S.`, `O'higgins`).

## Components

| Path | Purpose |
|---|---|
| `parsing/InputParser.kt` | Entry point: `parse` → `ParseOutcome`, `parseAndConvert` → `Outcome`. Local defaulting; a missing time (bare zone, `now`) is the wall clock in the resolved source zone. |
| `parsing/InputTokenizer.kt`, `NormalizedInput.kt` | Normalise with a raw-offset map; time or `now` at the start; split on the first standalone `in`/`to`; structural bare-zone test. |
| `parsing/TimeTokenParser.kt`, `ParsedTime.kt` | The `<time>` grammar, compact forms included. |
| `parsing/ZoneResolver.kt` | `ZoneResolver`, `ZoneResolution`, `ZoneResolverChain`. |
| `parsing/AliasZoneResolver.kt` | Step 1 and its table, verbatim. |
| `parsing/FoundationAbbreviationZoneResolver.kt` | Step 2, the Foundation snapshot and the curated expanded names. |
| `parsing/TimeZoneDatabaseCityResolver.kt` | Step 3 with the area allow-list and the legacy-link guard. |
| `parsing/CountryZoneResolver.kt`, `CountryZoneTable.kt` | Step 4: canonical clocks, and the no-clock countries (plus Antarctica) that prompt. |
| `parsing/OfflineFallbackZoneResolver.kt` | Step 5, the gazetteer decoded with kotlinx-serialization. |
| `parsing/ZoneRepresentativeCities.kt` | Item 21's cities: the abbreviation tables read backwards, self-consistency rule. |
| `parsing/ZoneSuggestionEngine.kt`, `EditDistance.kt`, `ZoneVocabulary.kt` | Did-you-mean: ≤2 edits (≤1 on short tokens), no code-for-code guesses, places first, then chain order, top 3. |
| `parsing/Prompt.kt`, `RawTextRange.kt`, `ParsingModels.kt` | P1/P2/P4/P5 with the spec copy, sides and raw ranges; shared models. |
| `engine/` | `WallClockResolver` (DST policy), `ConversionEngine`, `Formatting`, `ZoneNames` (iOS-origin zone names), `ResolvedZone`/`ZoneLabel`. |
| `presentation/` | `ConverterPresenter`, `ConverterDisplayDriver` (600 ms debounce), display state, chips, `PosterLayoutMode`. |
| `worldclock/` | Favourites and the world clock (item 32, port of Swift `WorldClock/`): `FavouriteDestination` (Swift's id rule, `resolvedZone`, `resolvingTypedZone`), `FavouritesStore` over an injected `KeyValueBacking` (Swift's Codable JSON under `favouriteDestinations`), `WorldClock.readings` + `ShiftedLocalClock`, `WorldClockDisplay`/`WorldClockRow`, `WorldClockFormatting`. |
| `fixtures/` | The shared fixture schemas (`ConversionCase`, `WorldClockCase`) and loader. |

Tests mirror the Swift suites' shape (`ZoneResolverChainTests`,
`InputTokenizerTests`, `InputParserTests`, `ZoneSuggestionEngineTests`, …) on
a representative subset; the fixture suites carry the end-to-end contract.
